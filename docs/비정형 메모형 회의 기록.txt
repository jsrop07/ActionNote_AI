어제 오후부터 오늘 오전까지 주문 상세 페이지 개편 관련해서 나온 이야기들 정리. 정식 회의록은 아니고, 개발팀 채널에서 나온 내용이랑 PM이 따로 남긴 코멘트를 섞어서 적어둔다.

일단 이번 주문 상세 페이지 개편은 “전체 리뉴얼”이 아니라 운영자가 자주 확인하는 정보 위주로 재배치하는 방향으로 가는 게 맞다. 처음에는 주문 정보, 결제 정보, 배송 정보, 환불 정보, 고객 문의 내역까지 한 화면에 다 넣자는 의견이 있었는데, 그렇게 하면 화면이 너무 복잡해질 것 같다. 이번 1차 배포에서는 주문 기본 정보, 결제 상태, 배송 상태, 환불 요청 여부만 먼저 정리한다. 고객 문의 내역은 CS 시스템 연동이 필요해서 이번에는 하지 않는 게 맞다.

PM은 운영자가 가장 많이 보는 정보가 주문번호, 고객명, 결제 상태, 배송 상태, 환불 요청 여부라고 했다. 프론트에서는 이 5개를 상단 요약 카드로 보여주고, 상세 정보는 아래 탭으로 나누는 안이 나왔다. 다만 탭을 너무 많이 만들면 오히려 불편할 수 있으니 주문/결제/배송 정도로만 나누자는 의견이 많았다.

백엔드 쪽에서는 기존 주문 상세 API가 이미 있긴 하지만, 필요한 데이터가 한 번에 내려오지 않는다. 현재는 주문 API를 호출한 뒤 결제 API와 배송 API를 각각 다시 호출하고 있어서 화면이 뜰 때 요청이 여러 번 발생한다. 백엔드 담당자는 주문 상세 전용 통합 API를 하나 만드는 게 낫다고 했다. 단, 환불 요청 상태까지 포함하려면 환불 테이블 조인이 필요하고, 이 부분은 쿼리 성능을 확인해야 한다. DBA 확인이 필요할 수도 있다.

오늘 결정된 건 일단 1차 배포 범위다. 주문 기본 정보, 결제 상태, 배송 상태, 환불 요청 여부까지 포함한다. 고객 문의 내역, 운영자 메모 기능, 주문 변경 이력 타임라인은 이번 배포에서 제외한다. 특히 주문 변경 이력 타임라인은 있으면 좋지만 데이터 정합성 검증이 필요해서 지금 넣으면 위험하다.

해야 할 일도 몇 개 있다. 프론트 담당자는 주문 상세 화면 와이어프레임을 내일 오전까지 정리한다. 백엔드 담당자는 주문 상세 통합 API 응답 필드 초안을 오늘 오후까지 작성한다. 환불 요청 여부를 어떤 기준으로 판단할지는 아직 명확하지 않다. PM이 운영팀에 실제 환불 요청 상태 기준을 확인해야 한다. 이건 마감일을 오늘 안으로 잡을지 내일 오전으로 잡을지 아직 정하지 않았다.

리스크도 있다. 첫째, 주문 상세 통합 API를 새로 만들면서 기존 API와 응답 기준이 달라질 수 있다. 둘째, 환불 요청 여부를 단순히 환불 테이블 존재 여부로만 판단하면 이미 취소된 요청도 환불 요청으로 보일 수 있다. 셋째, 고객 문의 내역을 제외하면 운영자가 다시 CS 시스템을 열어야 해서 불편하다는 피드백이 나올 수 있다. 넷째, 프론트에서 정보를 카드와 탭으로 나누는 과정에서 모바일 화면이 좁아질 수 있다.

정리하면 지금 바로 해야 하는 건 화면 구조 확정, 통합 API 필드 정리, 환불 요청 기준 확인이다. 고객 문의 내역이나 주문 변경 이력 타임라인은 이번에는 욕심내지 말고 다음 단계로 미룬다. 누가 최종으로 고객 문의 제외 안내 문구를 쓸지는 아직 안 정했다. 배포 일정은 다음 주 수요일을 목표로 보지만, 환불 기준이 늦어지면 하루 정도 밀릴 수 있다.
